# Laravel Octane 接口性能优化实录：从数据库迁移到 P99 97ms

> 2026-08-13

最近对一个 Laravel 在线校验接口做了一轮专项优化。这个接口需要完成店铺信息查询、SKU 规则校验、权限判断，并调用一个下游数据服务。业务预计流量可能增长到当前的十倍，而旧链路还依赖一套更适合分析查询、并不适合在线高并发的数仓。

最初的目标是消除在线请求对数仓的依赖。做到这一点之后，优化却没有结束：PHP-FPM 切换到 Octane 暴露了 DNS 延迟，HTTP 连接复用改变了瓶颈位置，Dingo 和权限中间件成为主要开销，一次看似合理的“绕过框架”优化甚至让 10 QPS 下的 P99 从亚秒级恶化到 7 秒以上。

最终，在保留原有鉴权和路由体系的前提下，入口真实 P99 从约 140ms 降到 97ms，10 QPS 下 150 个请求全部成功。

这篇文章记录的不只是最后改了什么，也包括几次判断错误，以及如何用分层日志把它们纠正回来。

## 起点：不要让分析型数据库承担在线高并发

旧接口的库存兜底逻辑会访问分析型数据库。平时流量不高时，它的延迟看起来尚可，但这类架构有两个隐患：

1. 在线接口与报表、同步任务共享分析资源，尾延迟容易被离线负载影响。
2. 流量扩大十倍后，短查询数量本身会成为压力，平均延迟正常并不能证明并发能力足够。

改造方向不是给慢查询前面加缓存，而是让在线事实数据回到事务数据库：

```text
在线校验
  → 批量读取虚拟 SKU
  → 没有库存候选时直接返回
  → 有候选时批量读取库存及授权关系
  → 全程不访问分析型数据库
```

这里有几个重要约束：

- 不逐个 SKU 查询，避免 N+1。
- 输入 SKU、SPU 和组合 SKU 先去重。
- 只读取校验需要的字段，不做分页、排序和展示字段拼装。
- 数据库异常时明确失败，不静默回退到分析型数据库。
- 不急着引入 Redis；精确批查达标后，多一层缓存只会增加一致性成本。

## 先识别真正会进入慢路径的请求

一开始对库存候选非空比例的判断并不可靠。与其根据业务印象决定架构，不如直接分析真实 SQL 和请求日志。

校验虚拟 SKU 后，增加最简单的短路：

```php
if ($suspectedStockSkus->isEmpty()) {
    return $validatedByVirtualSku;
}
```

它保证普通请求不会继续调用库存服务，也不会查询用户、部门和库存关系表。这个改动很小，却决定了后续 MySQL 路径的真实调用频率。

这类短路必须从公开入口写行为测试，至少断言：

- 结果与旧逻辑相同；
- 库存数据源调用次数为零；
- 审核失败、删除、跨部门等错误优先级不变。

## MySQL 批查比 Redis 更适合作为第一步

库存路径改用事务数据库后，查询分成两轮：

1. 按去重后的 SKU、SPU 批量读取有效库存记录。
2. 只对实际命中的人工库存 SKU，批量读取用户和部门关系。

必要索引形态类似：

```text
stock_skus(sku)                 UNIQUE
stock_skus(spu)                 UNIQUE
stock_sku_users(sku, user_id)   UNIQUE
stock_sku_parts(sku, part_id)
```

授权直接比较稳定 ID，而不是先把 ID 转成名称再比较：

```php
$allowedByUser = in_array($product->userId, $stockSku->userIds, true);
$allowedByPart = in_array($product->partId, $stockSku->partIds, true);
```

这样不仅减少两次字典查询，也避免名称修改、重名和不同数据源同步时差导致的不一致。

为什么没有给用户和部门表加 Redis？因为这些表最终只需要一次精确批查，延迟已经很低；缓存会引入失效策略、双写顺序和故障降级语义，却不一定能改善 P99。优化不是看到查询就加缓存，而是先证明它值得被缓存。

## 从 PHP-FPM 到 Octane：收益到底来自哪里

这轮改造同时把接口从 PHP-FPM 迁到了 Octane。只说“换成常驻进程，所以更快”是不完整的，因为两者的性能模型完全不同。

PHP-FPM 每个请求由独立 Worker处理。Laravel应用通常已经通过 OPcache减少了源码编译成本，但容器解析、服务实例和 HTTP Client等请求态对象仍会随请求重新准备。它的优点是隔离清晰：一个请求结束后，大部分状态自然释放；缺点是很难跨请求复用昂贵对象和下游连接。

Octane则让应用常驻内存：

```text
PHP-FPM
  请求 → Worker → 准备请求态对象 → 建立下游连接 → 返回

Octane
  Worker启动 → 引导Laravel一次
             → 请求1 ┐
             → 请求2 ├→ 复用安全的服务实例和HTTP连接
             → 请求3 ┘
```

对这个接口而言，Octane真正有价值的不是省掉一次Laravel启动，而是让下游HTTP连接可以跨请求复用。连接热起来以后，绝大多数请求的DNS、TCP connect和TLS指标都变成0，下游调用主要只剩服务处理和网络往返。

### 迁移前后经历了什么

这次迁移并不是切换运行模式后立刻变快，而是经历了四个阶段：

| 阶段 | 观测结果 | 说明 |
|---|---:|---|
| PHP-FPM参考基线 | P99约140ms | 旧链路入口指标，作为目标参照 |
| Octane刚部署 | 单请求约1.05s | DNS首选服务器超时，不是PHP执行慢 |
| DNS修复、连接尚未稳定复用 | 常见请求约140～180ms | TLS仍频繁占60～90ms |
| 连接复用和业务链路优化后 | Ingress P99 97ms | 10 QPS、150请求、全部成功 |

从约140ms到97ms，入口P99下降约31%。但这31%不能全部记在Octane头上，因为同期还完成了：

- 分析型数据库退出在线链路；
- MySQL批查和空候选短路；
- 店铺与部门查询从两次合并为一次；
- 删除两段与该接口无关的全局中间件工作。

可以明确归因于Octane的是：它提供了跨请求复用HTTP连接的生命周期基础。可以明确归因于业务优化的是：Controller和数据库阶段本身变短。最终结果是两者叠加，而不是一次运行时替换的魔法。

### 为什么不能照搬FPM里的单例写法

FPM中的“单例”通常只活一个请求，请求结束后自然销毁。Octane中的容器单例可能伴随Worker处理成百上千个请求，两者名字相同，生命周期却完全不同。

迁移时必须逐一检查单例是否持有：

- 当前请求、当前用户或Token；
- 可变数组、Promise或未完成任务；
- 上一次请求的异常和统计信息；
- 不具备并发安全保证的Handler状态。

HTTP Client及其连接池适合在明确生命周期后复用，但请求参数、Promise和结果不能留在单例属性中。否则FPM下从未出现的串请求、状态污染和内存增长，会在Octane下变成概率性故障。

这也是为什么本轮对全局Kernel Pipeline格外谨慎：Octane优化不能只验证单请求功能，还必须在固定Worker数下验证并发、P95和P99。

## Octane 把一个 DNS 问题放大成固定一秒

切换 Octane 后，接口一度稳定慢约一秒。应用日志显示下游 HTTP 调用约 1.05 秒，但下游服务自身 P99 只有几十毫秒。

在 Pod 内直接测试 DNS：

```bash
time getent hosts service.example.invalid

curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://service.example.invalid/
```

结果非常有辨识度：

```text
DNS      ≈ 1.00s
connect  ≈ 1.01s
TLS      ≈ 1.04s
total    ≈ 1.05s
```

`/etc/resolv.conf` 中第一个 nameserver 不可达，第二个 nameserver 可以在约 10ms 内返回。当前容器的 resolver 按顺序等待第一个服务器超时，恰好贡献了固定的一秒。另一个基础镜像上的服务表现正常，只是 resolver 行为不同，并不代表某种 Linux 发行版天然更快。

基础设施修复 DNS 后，请求从约一秒回到百毫秒级。这个问题提醒我：看到 `bi_http_ms` 高，不要立刻归因于下游应用；DNS、TCP、TLS、TTFB 必须分开记录。

## HTTP/2 的收益来自复用，不是协议名称

DNS 修复后，单次下游调用仍有 60～90ms 的 TLS 开销。Octane 是常驻进程，本来具备复用连接的条件，但前提是 HTTP Client 及 Handler 也能跨请求安全复用。

最终日志中大多数请求表现为：

```text
dns_ms = 0
connect_ms = 0
tls_ms = 0
```

说明连接复用已经生效。下游 HTTP P99 降到约 35ms。

不过不能因为协商出了 HTTP/2 就宣称获得了多路复用收益。如果压测工具每次创建新连接，或者客户端连接池限制导致请求在本地排队，最终数字仍然会失真。协议、连接生命周期和压测调度是三件不同的事。

## 分段日志要覆盖整个请求，而不只是 Controller

这轮排查最有价值的产物，是一条请求只打一条结构化完成日志：

```json
{
  "event": "sku_verify_completed",
  "request_id": "...",
  "input_sku_count": 1,
  "expanded_sku_count": 2,
  "pre_route_ms": 35,
  "controller_ms": 22,
  "domain_ms": 3,
  "bi_http_ms": 16,
  "verify_log_ms": 3,
  "php_request_ms": 58,
  "status": "success"
}
```

日志不记录完整 SKU、域名和请求体，只记录数量和阶段耗时。配合统一的 Request ID，可以把客户端、Ingress、Laravel 和下游服务逐条关联。

分段后，10 QPS 下的服务端组成非常清楚：

| 阶段 | P50 | P99 |
|---|---:|---:|
| Laravel 请求总耗时 | 58ms | 91ms |
| Controller 之前 | 35ms | 59ms |
| Controller | 22ms | 43ms |
| 下游 HTTP | 16ms | 35ms |
| 店铺与部门查询 | 3ms | 8ms |
| 校验日志 | 3ms | 3ms |

到这里，继续优化库存 SQL已经没有意义。主要空间转移到了路由、Passport、权限和全局中间件。

## 一次失败的优化：为单个接口绕过 Dingo

性能剖析显示，Dingo 路由注册和 Spatie 权限模型恢复占据了不少前置时间。于是我尝试为这个接口注册一条原生 Laravel 路由，并在 Kernel 中精确跳过 Dingo 请求中间件。

功能测试全部通过：

- 正常请求返回 200；
- 未登录返回 401；
- 参数错误返回 422；
- 异常格式与旧接口一致；
- 其他路由仍由 Dingo 处理。

本地小样本甚至显示单次请求快了约 100ms。然而部署后，10 QPS 的客户端 P99 超过 7 秒。

进一步做严格 A/B：同一镜像、同一环境变量、同样两个 Octane Worker、相同请求体和并发参数。预热后的 100 请求结果显示：

| 指标 | Dingo 基线 | 原生路由方案 |
|---|---:|---:|
| 吞吐 | 2.61 QPS | 2.39 QPS |
| P50 | 728ms | 761ms |
| P95 | 853ms | 1336ms |
| P99 | 948ms | 1582ms |

问题集中在自定义 Kernel Pipeline。它改变了 Octane 常驻进程中的请求分发路径，局部少做了一些工作，却引入了更严重的并发尾延迟。

最终完整撤销了原生路由、Kernel 重写和异常适配，继续保留 Dingo。

这次失败给了一个比成功优化更重要的结论：

> 框架入口上的“小改动”不是局部改动。功能对等不代表并发语义对等，小样本平均值也不能证明 P99 改善。

## 真正安全的做法：删除与接口无关的工作

保留 Dingo 后，继续审查全局中间件，发现同一个请求会执行两类与在线校验无关的逻辑。

### 响应阶段的第二次权限检查

接口路由本身已经执行必要的业务权限校验。但全局响应中间件还会检查用户是否拥有“查看用户信息”权限，只是为了决定是否返回密码修改提示头。

这个在线校验调用方不使用该能力，因此只对精确的 POST 路径跳过第二次权限检查，提示头仍返回兼容的默认值。业务权限没有取消。

### 用户活跃时间更新

另一个全局中间件会再次解析 JWT、查询用户，并在满足条件时同步更新最后活跃时间。对于高频机器调用接口，这既不是鉴权，也不是业务校验。

最小实现就是精确短路：

```php
if (
    $request->isMethod('POST')
    && $request->path() === 'api/store/vs_sku/status'
) {
    return $next($request);
}
```

测试不仅覆盖目标接口跳过逻辑，还必须证明：

- 同路径 GET 不跳过；
- 相似 POST 路径不跳过；
- Passport鉴权和路由权限仍然执行。

本地增量 A/B 中，这个改动带来约 5%的吞吐提升，P50 和 P95 分别下降约 4%。收益不大，但边界明确、长期语义合理。

## 压测工具也会说谎

一次 Node.js `fetch` 压测显示：10 QPS 时客户端 P99 为 842ms。与此同时，Laravel日志中的 P99 只有 90ms。

如果只看客户端数字，很容易得出“Octane Worker 已经排队”的错误结论。把同一批 150 个 Request ID 与 Ingress日志关联后，结果是：

| 指标 | P50 | P95 | P99 | 最大值 |
|---|---:|---:|---:|---:|
| Ingress 请求耗时 | 62ms | 85ms | 97ms | 98ms |
| Upstream 响应耗时 | 62ms | 86ms | 97ms | 98ms |
| Laravel 请求耗时 | 58ms | 81ms | 91ms | 91ms |
| Ingress 与 Laravel 差值 | 4ms | 11ms | 21ms | 24ms |

150 个请求全部使用 HTTP/2，全部返回 200，并且在约15秒内完整到达 Ingress。Ingress与 upstream 耗时几乎一致，不存在网关排队。

所以那多出来的几百毫秒发生在压测客户端内部：连接池、事件循环调度或请求发起前的等待被计入了 `fetch` 总耗时。

最终验收选择 Ingress `_request_time`，而不是只相信某个压测工具的汇总。

## 最终结果

在固定10 QPS、150请求的测试中：

- 成功率：100%；
- Ingress P50：62ms；
- Ingress P95：85ms；
- Ingress P99：97ms；
- 最大值：98ms；
- 在线链路不再访问分析型数据库。

相较原先约140ms的P99，下降约31%。它还没有达到80ms的理想目标，但已经非常接近，而且结果来自入口日志与应用日志的逐请求交叉验证。

## 这轮优化真正有用的方法

回头看，最有效的不是某个具体框架技巧，而是下面这套顺序：

1. **先改数据边界**：让在线请求使用在线数据源，而不是用缓存掩盖错误架构。
2. **先统计慢路径比例**：用真实日志决定要优化哪条分支。
3. **批量查询并尽早短路**：避免 N+1，也避免无候选时做无意义工作。
4. **记录 DNS、连接、TLS、TTFB**：不要把所有 HTTP耗时都归给下游服务。
5. **把日志做到请求级关联**：客户端、Ingress、应用和下游必须共享 Request ID。
6. **本地 A/B必须严格同环境**：同镜像、同 Worker、同数据、同预热、同顺序，并做反向顺序复测。
7. **P99优先于平均值**：小样本和单请求变快，都可能掩盖并发回退。
8. **优先删除无关工作**：比绕开框架、复制权限缓存或引入新基础设施更安全。
9. **缓存不是默认答案**：只有确认数据库已是瓶颈，并能定义一致性语义后才值得引入。
10. **失败方案要完整撤销**：不要因为已经投入时间，就保留一套无法证明并发安全的复杂实现。

性能优化经常不是一路变快，而是不断修正测量方式。最后减少的几十毫秒固然重要，更重要的是知道这些毫秒究竟发生在哪里，以及为什么可以安全地删掉它们。
