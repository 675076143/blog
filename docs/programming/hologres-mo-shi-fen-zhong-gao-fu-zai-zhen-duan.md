# Hologres 每小时第 20 分钟高负载诊断

> 2026-07-26

## 现象

Hologres 在每小时的第 20 分钟出现 CPU / 连接数高峰，部分 API 请求返回 HTTP 499。

## 分析过程

### 初始假设

以为某外部服务在 `:20` 的两个定时任务是主因，验证后发现它们只是叠加因素之一。

### 实际路径

1. 读取全部 811 行 Kernel.php → 找出所有 `:20` 相关的 cron
2. 读取所有 schedule 文件 → 对比确认
3. 读取 4 个 CSV 日志文件（慢查询、cron 执行、请求日志）
4. 逐条交叉比对时间戳、SQL 语句、请求路径

## 根因

### 主犯：内部 4 个 cron 在 `:20` 同时触发

| # | Cron | 影响 |
|---|---|---|
| C1 | `handleXxxMonitor` 每小时 :20 | **主犯** — 8 次 Hologres 查询串行持续 **7.4 秒** |
| C2 | `scanning` 每 5 分钟（含 :20） | 查询 + 大量预查询 |
| C3 | `scanning` 每 10 分钟（含 :20） | JOIN 全表子查询 |
| C4 | `checkMismatch` 每分钟 | 快速完成，占一个连接 |

### 叠加因素：外部服务在 :20 涌入的 HTTP 请求

| # | Cron | 影响路径 |
|---|---|---|
| A1 | `sync:payment_info` 每小时 :20 | → POST API |
| A2 | `sync:option_info` 每小时 :20 | → POST API |

### CPM Monitor 为何是主犯

```typescript
async getIndex() {
    const list = [['US', '美国'], ['GB', '英国'], ['DE', '德国'], ['FR', '法国']];
    for (let i = 0; i < list.length; i++) {  // <-- 串行! 4国逐个执行
      // 每次 ~100-400ms
    }
}
```

8 次 knex 查询，每次 ~100-400ms，`for` 串行 + 飞书消息发送 = 总耗时 **7.4 秒**。关键不在于连接数，而在于**持续 7.4 秒占用连接**。

### 叠加效应时间线

```
:20:00 — [C4] 快速完成
:20:00 — [C1] 开始串行查询
:20:00 — [C3] 开始
:20:00 — [C2] 开始
:20:01 — [C2] 完成
:20:02 — [C3] 完成
         ↓ C1 仍在运行
:20:03 — 外部 HTTP 请求涌入
         ↓ C1 持续占用连接
:20:07 — [C1] 完成（总耗时 7.4 秒）
         ↓ 连接池持续紧张
:20:33 — API 开始超时 499
```

## 修复建议

### P0 — 错峰调度

| 改动 | 当前 | 目标 |
|---|---|---|
| C1 | `20 * * * *` | `15 * * * *` |
| C2 | EVERY_5_MINUTES | 偏移 2 分钟 |
| C3 | EVERY_10_MINUTES | 偏移 3 分钟 |
| 外部 cron ×2 | `20 * * * *` | `40 * * * *` |

### P1 — 优化

| 改动 | 当前 | 目标 |
|---|---|---|
| C1 串行改并行 | `for...await` | `Promise.all`（4 国同时） |
| SQL 优化 | 全表关联 | 加索引 |

## 关键经验

1. **慢查询 ≠ 负载来源**：每次 100-400ms 不会出现在慢查询日志，但串行 8 次 = 持续占用连接 7.4s
2. **cron 叠加是常见隐患**：多个服务的 `:00`/`:10`/`:20` 整点触发容易产生峰值
3. **交叉验证日志文件**：慢查询 + cron 日志 + 请求日志三者交叉比对才能定位完整链路
