# 我是怎么放弃 RAG 和 MCP，回归朴素文件操作的

> 2026-07-26

之前基于 Karpathy 的 LLM Wiki 模式搭了一套知识库，配合 qmd 做语义搜索、MCP 做标准化写入接口，自认为还挺先进。用了一段时间，全拆了。

## 曾用的方案

两个核心组件：

1. **qmd** — BM25 + 向量搜索 + LLM 重排序的混合检索。每次对话自动搜 wiki，把相关内容注入上下文。
2. **notes-wiki MCP** — 注册为全局工具，提供 `add_page`、`update_page` 等标准化的知识库写入接口。

## 为什么放弃了

### Token 开销扛不住

qmd 的标准流程：搜索 → 重排序 → 取全文 → 注入上下文。每轮对话都要走一遍这个链路。本地跑模型（24GB VRAM，~32K 上下文），塞几篇 wiki 页上下文就满了。即使走 API，搜索 + 重排序 + 全文注入三次 token 开销，也是实打实的成本。

### 模型已经不需要知识库了

我的 wiki 里记的大部分内容——Linux 排查、Docker 选型、PHP 调优——早就进了模型的训练数据。它不需要我帮它"补充知识"，它自己就知道。知识库真正有价值的地方是**项目独有的内部知识**，但我日常问的偏通用，不太触及这个场景。

### LLM 自己就是最好的"搜索工具"

现在的工作方式简单得多：

- **翻阅：** "看看 wiki/pages/xxx 关于 xx 的内容" — LLM 自己 grep、read，决定看什么、怎么看
- **记录：** "帮我记一下：今天发现 xxx" — LLM 自己建文件、写 frontmatter、更新 index

不需要一个 MCP 工具来告诉我"怎么搜"或"怎么写"。LLM 理解规范之后，普通文件操作就是最高效的接口。

## 现在的认知

Wiki 的真正价值在于**整理输出**，而不是**运行时补充知识**。它更适合作为博客素材库——平时随手记，有空整理成文章发出去——而不是每次对话都被动注入的上下文。

RAG 和 MCP 解决的是"模型不知道的事"——你的私有 API 文档、内部数据库 schema、遗留代码细节。如果你的 wiki 里主要是"Linux 怎么挂载 NAS"这种通用问题，那它应该是一本你已经写完的书，而不是一个需要实时查询的数据库。
